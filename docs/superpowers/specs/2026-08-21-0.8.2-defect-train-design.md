**Date:** 2026-08-21
**Status:** Approved design (brainstorm 2026-08-21, post-0.8.1)
**Decides:** GitHub #79 (dangling-link false-positives every `../` wikilink),
#76 (hub typing inconsistent across three page shapes), #78 (ten deferred

## 1. Evidence (why now)

0.8.1 shipped the seam fixes and the `/ren:update` to 0.8.1 ran clean —
`frontmatter-type-1` stamped its one remaining page, the page-type chain
reported no pending work, and `/ren:doctor` came back **0 warn / 0 error**.
The train below is what that clean run did *not* cover.

Measured on the live wiki, 2026-08-21 (post-update):

- **28 pending suggestions: 21 quarantine-release, 7 wiki-health lint.**
  The lint seven break down as 2 `dangling-link`, 3 `map-pointer-missing`,
  1 `hub-split-link-lists`, 1 `missing-frontmatter-type`.
- **Both `dangling-link` findings are false.** `projects/hallm/knowledge/
  codebase/codebase.md` and `.../experiment/training-setup.md` each carry a
  valid `../` wikilink that resolves on disk. `_resolves()` says otherwise.
- **The `missing-frontmatter-type` finding is already stale** — the
  0.8.1 migration typed that page during today's update. It has not
  self-closed only because no wiki-health run has happened since.
- **Four stale `.venv` directories** sit in the versioned plugin cache
  (0.7.6, 0.7.7, 0.7.9, 0.8.0). #40 records one; nothing removed the rest.
- **The recorded fast-path interpreter is a dangling path.**
  `interpreter.json` names
  `.../cache/ren-os/ren/0.6.1/.venv/bin/python3`, warmed 2026-07-31. Version
  0.6.1 is no longer in the plugin cache. Roughly ten releases have shipped
  since, and no check covers this record.

Three of the seven lint findings are therefore closable by machine, and the
train's headline acceptance number falls out of that: **7 → 4, no human
decisions**.

## 2. Part A — dangling-link containment (#79)

### 2.1 The defect

`skills/wiki-health/lib/lint.py`, `_resolves()`:

```python
for base in (wiki_root, (wiki_root / page).parent):
    try:
        if ren_paths.safe_join(base, cand).is_file():
```

`safe_join` enforces containment against its **first argument**. On the second
iteration that argument is the page's own parent directory, so any candidate
beginning `../` escapes *that* directory by construction, raises
`PathTraversalError`, and is swallowed by the enclosing `except ... continue`
— even when the target lands well inside the wiki.

Resolution base and containment boundary are two different concerns. The code
conflates them by passing one value for both.

### 2.2 The fix

Resolve the candidate against the page's parent; validate containment against
`wiki_root`. The traversal guard stays — a link that genuinely escapes the
wiki must still be refused — it simply guards the right boundary.

### 2.3 Why the regression test must be fence-free

Both live false positives happen to sit on pages containing a code fence,
and that is the **only** reason they were reported rather than rewritten.
`_link_findings` treats an unambiguous basename match as a safe automatic
repoint (`dangling-link-repointed`); the fence is what suppressed it. A
regression test on a fenced fixture would pass while the actual hazard — a
silent data-plane write repointing a correct link — survived untouched.

The test asserts a `../` link on a fence-free page is **neither reported nor
rewritten**. A wiki-wide sweep today finds 2 misjudged links, 0 of them
auto-rewritable; nothing has been corrupted, and the path is live.

### 2.4 Sequencing constraint

Part A lands **first and alone**, before any other part of this train. Its
acceptance is a measurement against the live wiki (§8), and bundling it with
unrelated changes makes that measurement unattributable.

## 3. Part B — hub typing (#76)

Three disagreements were filed. Invariant I1 (derivation never overrides an
existing `type:`) preserved all of them rather than silently renaming pages,
so each is a decision, not a bug. Nothing reads `type:` to make a decision
today — the point of settling now is that something eventually will.

### 3.1 Root `index.md` stays `l2-map`

**Decided:** disk wins. `index.md` is typed `l2-map`, it was migrated under
that page type by `l2-map-1-to-2` in 0.7.0, and the migration chain still
registers it there. The lint's `_is_hub_page()` is what changes.

Consequences: 0 pages rewritten, the `l2-map` schema chain untouched.

### 3.2 One predicate, in `lib/`, imported by the lint

`lib/memory/page_types._is_folder_note_hub` and
`skills/wiki-health/lib/lint._is_hub_page` encode the same idea, written
independently, and they diverge (page_types excludes `index.md`; the lint
does not).

The issue records a layering reason not to share them. That reason does not
hold: the constraint is that `lib/` must not import from `skills/`, and the
dependency here runs the other way. `lint.py` already imports
`lib.memory.journal`, `lib.memory.quarantine` and `lib.memory.queue`.

**Decided:** `_is_folder_note_hub` in `lib/memory/page_types.py` is the single
predicate for the **folder-note question only**. `lint._is_hub_page`'s
folder-note branch is deleted and delegates to it; the lint's separate
`index.md` branch **stays exactly as it is**.

This is the correction that matters, and it reframes the whole issue: the two
functions were never asking the same question.

| Function | Question it answers | `index.md` |
|---|---|---|
| `page_types.derive_type` | What `type:` should this page carry? | `l2-map` (§3.1) |
| `lint._is_hub_page` | Should hub-entry maintenance run on this page? | **yes** |

Root `index.md` is the wiki spine, and `_hub_missing_entries` keeping its
bullets current is a real, wanted behavior; the lint's `index.md` branch also
covers legacy `**/index.md` hubs predating folder-note-hubs-1. Deleting that
branch to make the two functions agree would stop maintaining the spine in
order to win a naming argument.

Only the folder-note *sub-predicate* is genuinely duplicated — written twice,
independently, with the same `projects/`-scoping and the same exclusion set.
That, and only that, is what gets unified.

**Part B is therefore behaviorally neutral by construction**, not by
measurement: no page changes type, no rule changes which pages it fires on.
§3.4's sweep is a regression check, not the mechanism of proof.

The remaining `index.md` divergence is intentional and documented at both
sites — two functions, two questions, two right answers.

### 3.3 Global `lessons/lessons.md` — a narrow rule, not a wider predicate

`derive_type()` returns `lesson` for the root-level `lessons/lessons.md`
(rule 3), while disk says `hub`. The disagreement is unreachable in practice:
`_ensure_lessons_hub()` is the sole producer of that page and its pre-stamp
always wins under I1. The table still lies.

**Decided:** add a narrow rule 2b — root-level `lessons/lessons.md` derives
`hub` — and leave `_is_folder_note_hub` untouched.

Rejected: widening the predicate by dropping its `projects/` scoping. It is
the conceptually honest generalization, but the predicate is now shared
(§3.2), so the lint inherits any widening: more pages become hubs, and rules
like `hub-split-link-lists` begin firing on them. The scoping is also
deliberate — it exists so a project literally named `knowledge` cannot
false-positive. Buying table-honesty at the cost of an unmeasured lint blast
radius is the wrong trade in a defect train.

Accepted cost: "what is a hub" is now encoded in two places. Rule 2b carries a
comment pointing at this section.

### 3.4 Invariant

Part B rewrites **no pages** and produces **no new lint findings**. Both are
asserted, not assumed: a full lint sweep before and after must return the same
finding set.

One sentence of nuance (final-review finding 6, 2026-08-22): rule 2b changes
`derive_type("lessons/lessons.md")` from `lesson` to `hub`, and `derive_type`
feeds `ensure_type` upstream of the queue's noop-duplicate comparison. On the
live wiki that page is already typed `hub`, so "0 pages rewritten" holds
there — but on a wiki where `lessons/lessons.md` is untyped, Part B WOULD
stamp `hub` where it previously stamped `lesson`. That is the wanted outcome
of settling the disagreement, not a violation of the invariant; the blanket
"rewrites no pages" wording above just does not admit it on its own.

## 4. Part C — deferred minors (#78), eight of ten

### 4.1 The recheckable gate is ordered wrongly

In `_retract_resolved_findings`, the `rule not in _RECHECKABLE_RULES: continue`
gate precedes the page-read that retracts findings on deleted pages. A
`held:<cls>` or `blocked:<cls>` finding against a page that no longer exists
therefore stays pending until the 30-day expiry.

**Fix:** hoist the page-existence check above the rule gate. A page being gone
is a *fact*, not a re-judgment — the reason the gate exists (never read the
absence of a fresh judgment as "resolved") does not apply to it. This strictly
increases correct retractions and cannot resolve a claim it did not check.

### 4.2 `prov is None` means two different things in wrap

`propose_and_apply` returns `prov is None` both for a genuinely held pending
write *and* for a noop-duplicate — content that normalized equal to disk,
yielding a synthetic, never-persisted entry whose qid is absent from the queue
directory. Wrap's update and create branches conflate them, so an unchanged
re-run reports an item as `held` citing a qid the friend cannot look up.

The discrimination already exists twice in the codebase: at wrap's own L1
branch (#49) and in the 0.8.1 lint fix. **Fix:** apply the same pattern at the
two remaining call sites. No new mechanism.

### 4.3 The remaining six

| Item | Fix |
|---|---|
| `decide()` docstring enumerates only accepted/declined/expired as immutable | Add `resolved`, which it already rejects |
| `_RESOLVED` (private) exported in `__all__` | Rename to `RESOLVED`; the issue's own condition — "if this file is touched for anything else" — is met |
| No test retracts an already accepted/declined/expired entry | Add the three cases; only resolved→resolved is covered today |
| `test_real_secrets_still_hit` lacks the exact #72 boundary | Parametrize the case: a guard word, a non-terminator character, then a terminator. **Assemble the fixture at runtime — never as a source literal.** See §7 |
| `test_merges_transport.py` imports mid-file | Move to top |
| Two `rglob` passes per `run_incremental_lint()` | Left as-is — see §4.4 |

### 4.4 Two minors stay, deliberately

`frontmatter-type-1/migrate.py`'s silent `continue` on an unreadable file
matches `trust-backfill-1`'s existing pattern, and wrap's raise-then-catch
matches the same file's other two call sites. Fixing only the named instance
would manufacture the inconsistency #78 was written to avoid; fixing the
siblings too would pull working, untouched files into a defect train for no
defect.

Each gets a one-line comment recording that consistency is the reason, so the
next reader does not re-derive this analysis. The double-`rglob` walk is a
performance observation on a tree of ~160 pages — noted, not acted on.

## 5. Part D — update's global tier

`/ren:update`'s closing steps call `rerender_all_project_claude_md()`, which
covers the **project** tier only. The **global** block in
`claude_user_dir()/CLAUDE.md` carries a doctrine index of absolute paths
pinned to the running version:

```
.../plugins/cache/ren-os/ren/<version>/doctrine/agent-orchestration.md
```

Nothing re-renders it on a version bump. After today's update those five paths
still read `0.8.0`. They resolve only because the 0.8.0 cache directory
happens to still exist; once it is GC'd they are dead links in a file injected
into every session.

**Fix:** `skills/update/SKILL.md`'s closing steps gain a global-tier step
beside the project one, calling the existing
`lib.adapter.claude_md.write_global_claude_md()`. Best-effort and
informational, exactly like its project-tier sibling — an update must not fail
on a CLAUDE.md render.

This is #64's shape one tier up: #64 wired the per-page re-render hooks and
closed the project-tier gap; the global tier was never in scope.

Today's stale block was already re-rendered by hand during the update
(`result: updated`, diff confined to the five version pins, everything outside
the markers preserved). Part D closes the recurrence, not the symptom.

## 6. Part E — cache-env remediation (#40)

### 6.1 Correction: the check is not broken

An earlier draft of this spec claimed `check_cache_env_hygiene` was blind
because it returned `skip` during the 0.8.1 update run. That claim was wrong
and is withdrawn.

The check resolves the cache root from `$CLAUDE_PLUGIN_ROOT`, which **is** set
when `/ren:doctor` runs as a plugin skill. The `skip` observed on 2026-08-21
came from invoking the check module directly via `uv run` without that
variable — the documented path, chosen deliberately so the check never warns
on a guess (`plugin_cache_versions_root()`: "callers must treat that as
'unresolvable', never as 'no live versions'").

The decisive evidence is the open-work ledger itself: its #40 line exists
*because the check warned*, on 2026-08-18. A blind check does not file
findings.

### 6.2 What is actually left of #40

Remediation, not code. Remove the four stale directories — 0.7.6, 0.7.7,
0.7.9, 0.8.0 — and close #40. They are regenerable uv environments.

Two exemptions must be honored, and neither is at risk here:

- **The current version's `.venv` is never stale.**
  `skills.install.lib.warm_environment` creates it on purpose and
  `interpreter.json` records an interpreter inside it (§8). The current
  version carries no `.venv` today, so the four removals cannot touch it.
- **`gc_stale_envs()` is a different location.** It prunes
  `framework_root()/.envs/<v>`, not the plugin cache, and correctly reported
  no removals during the update.

### 6.3 One narrow improvement, optional

When the framework is running *from* a versioned cache directory but
`$CLAUDE_PLUGIN_ROOT` is unset, the cache root is derivable from the running
module's own location. That is a fact about where the code is, not a guess,
so it does not violate the rule in §6.1 — and a repo checkout still resolves
to no cache and correctly returns `skip`.

This is a convenience for hand invocations, not a defect fix. It is the
lowest-value item in the train and the first thing to drop if the train needs
trimming.

## 7. Part F — `_watermark_after` boundary tests

`skills/distill/lib`'s `_watermark_after` boundary behavior — the

## 8. Part G — recorded interpreter freshness

### 8.1 The defect

`hooks/wake-up/ren-wake-up.py` re-execs itself under an interpreter recorded
at install time, specifically to avoid a cold-`uv` cost of roughly 7s that
trips `_REEXEC_TIMEOUT_S` on a slow start (#11 §4).

The recorded interpreter lives under `ren/0.6.1/`, a version the plugin cache
no longer contains. `_recorded_interpreter_path()` guards with `p.is_file()`,
gets `False`, returns `None`, and the hook falls through to the `uv run` path.

**It fails safe** — nothing is broken, no session errors. But every session
since the 0.6.1 cache directory was pruned has paid exactly the cost the fast
path exists to avoid, and the record has been stale since 2026-07-31 across
roughly ten releases.

### 8.2 Why nothing caught it

`warm_environment()` runs at install, not at update — so a version bump never
re-stamps the record. And of `/ren:doctor`'s 26 checks, none reads
`interpreter.json`. The failure is silent in both directions: the hook
degrades quietly by design, and no diagnostic looks at the record.

This is the same shape as Part D — a per-version artifact that only install
writes and only install refreshes.

### 8.3 The fix

A new `check_interpreter_freshness` in `skills/doctor/lib`, checked **in this
order** — a faithful mirror of `_recorded_interpreter_path()`'s own validity
test in `hooks/wake-up/ren-wake-up.py`, not an independent, weaker predicate:

| State | Result |
|---|---|
| No record at all | `info` — never warmed, not a defect |
| Recorded path does not exist on disk | `warn` — names the recorded version, says the fast path is degraded |
| Recorded path exists but is not named like a python binary | `warn` — the hook rejects it too |
| Recorded path exists, is named like a python binary, but is not executable | `warn` — e.g. a synced/restored `.venv` that lost its exec bit |
| Path valid but recorded for a different machine or platform | `warn` — the hook rejects the mismatch and falls through to cold uv |
| Path valid, current machine/platform, version ≠ current cache version | `warn` — stale record, re-warm suggested |
| Path valid, current machine/platform, current version | `ok` |

**Correction to an earlier draft of this table (final-review finding 6,
2026-08-22):** the machine/platform mismatch row does not warn *unconditionally*
first — dangling/invalid beats it. `platform.node()` is not stable for a
given physical machine (observed: this laptop's node name flips between a
hostname and an IP depending on network), so a record can be simultaneously
"foreign" by the machine/platform test and genuinely dangling on THIS
machine; checking machine/platform first would then `skip` on the exact
machine the check exists to warn about, and that ordering was itself a
shipped defect (final-review finding 2). Existence/name/exec-bit are checked
first because a dangling or invalid path is a fact about this machine
regardless of whose record it is.

Every rejection reason is `warn`, never `skip`: the hook REJECTS a record
that fails ANY of its conditions and falls through to cold `uv`, so the
practical consequence on this machine is always a degraded fast path — and
"re-warm via /ren:install" is correct, actionable advice regardless of which
condition failed. An earlier draft warned that a machine/platform mismatch
must not warn because `state_dir()` may be synced across machines; that
reasoning does not survive contact with the hook's actual behavior — the
hook ignores a foreign record too, which means the fast path really is
degraded on this machine, and `skip` would hide it. `skip` is not used by
this check.

### 8.4 Remediation

Re-run `warm_environment()` once so the record points at a live interpreter.
Re-warming is install's existing, tested path — this train adds no new
mechanism for it.

**Out of scope:** wiring a re-warm into `/ren:update`'s closing steps. That is
the right long-term fix and it is a behavior change to the update flow, which
this defect train should not make on the strength of one day's evidence. The
doctor check makes the condition visible; visibility is enough for 0.8.2.

## 9. Testing

TDD throughout. Every part below is a defect with observable behavior, so
every part gets a failing test before its fix.

- **Part A:** fence-free `../` fixture asserting neither reported nor
  rewritten; a genuinely escaping link still refused; the existing
  same-directory case unchanged.
- **Part B:** `derive_type()` table cases for root `index.md`, root
  `lessons/lessons.md`, and a project folder note; one predicate reachable
  from both call sites; full-sweep finding-set equality before and after.
- **Part C:** deleted-page retraction for a non-recheckable rule; unchanged
  re-run of wrap's update and create branches reporting neither a phantom
  `held` nor a qid absent from disk; the three decided-status retract cases;
  the #72 boundary case.
- **Part D:** rendered global block's doctrine paths track the running
  version; content outside the markers preserved byte-for-byte.
- **Part E:** if §6.3 is taken — cache root resolved from the module location
  when the environment variable is absent; a repo checkout still `skip`s; the
  current version's `.venv` still exempt. Otherwise Part E ships no code and
  no tests.
- **Part G:** `warn` on a dangling recorded path; `warn` on a valid path from
  a non-current version; `ok` on valid + current; `info` on no record; `skip`
  on a foreign machine or platform record.
- **Part F:** the two boundary cases named in §7.

### The push guard constrains one of these tests

`tests/lib/memory/test_scrub.py` carries an explicit comment stating that
fixtures below it must be assembled at runtime, because the pre-push guard
scans added lines with this very scanner. The 0.8.1 train was blocked twice
for putting secret-shaped literals below that line. The §4.3 boundary fixture
sits in that file and **must** be assembled at runtime.

Two further consequences, both learned the hard way in 0.8.1: the guard runs
the **installed** plugin's scrub, not the working tree's — so a verification
script written against a fixed local scrub can report CLEAN and be wrong — and
documentation of a scrub false positive cannot quote the offending string
literally. This spec describes the §4.3 shape rather than writing it.

## 10. Acceptance (run live, after the train lands)

1. **7 → 4 pending wiki-lint findings, zero human decisions.** The two false
   `dangling-link` findings and the stale `missing-frontmatter-type` finding
   self-close on the first wiki-health run. The 3 `map-pointer-missing` and 1
   `hub-split-link-lists` findings are genuine and must survive — a drop below
   4 is an over-retraction defect, not a better result.
2. **21 quarantine suggestions unchanged.** This train does not touch them.
3. **`/ren:doctor` reports `cache_env_hygiene: ok`** with the four stale
   directories gone — run as a plugin skill, not via a bare `uv run`, or the
   documented `skip` path makes the result meaningless (§6.1).
4. **`/ren:doctor` reports `interpreter_freshness: ok`** after the re-warm,
   having reported `warn` before it. The recorded path must exist on disk and
   name the current cache version.
5. **Full lint sweep finding-set identical across Part B** — same findings,
   same pages, same rules.
6. **A fresh `/ren:update` dry-run** shows the global doctrine block rendering
   at the running version.

Criterion 1 carries the same trap the 0.8.1 train hit: an over-retraction
would present as a *better-looking* number. The count is asserted with its
composition, never alone.
