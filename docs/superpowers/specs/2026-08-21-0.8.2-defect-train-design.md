## 2. Part A — dangling-link containment (#79)

### 2.1 The defect

`skills/wiki-health/lib/lint.py`, `_resolves()`:

```python
for base in (wiki_root, (wiki_root / page).parent):
    try:
        if ren_paths.safe_join(base, cand).is_file():
```

`safe_join` enforces containment against its **first argument**. On the second
iteration that argument is the page's own parent directory, so any candidate
beginning `../` escapes *that* directory by construction, raises
`PathTraversalError`, and is swallowed by the enclosing `except ... continue`
— even when the target lands well inside the wiki.

Resolution base and containment boundary are two different concerns. The code
conflates them by passing one value for both.

### 2.2 The fix

Resolve the candidate against the page's parent; validate containment against
`wiki_root`. The traversal guard stays — a link that genuinely escapes the
wiki must still be refused — it simply guards the right boundary.

### 2.3 Why the regression test must be fence-free

Both live false positives happen to sit on pages containing a code fence,
and that is the **only** reason they were reported rather than rewritten.
`_link_findings` treats an unambiguous basename match as a safe automatic
repoint (`dangling-link-repointed`); the fence is what suppressed it. A
regression test on a fenced fixture would pass while the actual hazard — a
silent data-plane write repointing a correct link — survived untouched.

The test asserts a `../` link on a fence-free page is **neither reported nor
rewritten**. A wiki-wide sweep today finds 2 misjudged links, 0 of them
auto-rewritable; nothing has been corrupted, and the path is live.

### 2.4 Sequencing constraint

Part A lands **first and alone**, before any other part of this train. Its
acceptance is a measurement against the live wiki (§8), and bundling it with
unrelated changes makes that measurement unattributable.

## 3. Part B — hub typing (#76)

Three disagreements were filed. Invariant I1 (derivation never overrides an
existing `type:`) preserved all of them rather than silently renaming pages,
so each is a decision, not a bug. Nothing reads `type:` to make a decision
today — the point of settling now is that something eventually will.

### 3.1 Root `index.md` stays `l2-map`

**Decided:** disk wins. `index.md` is typed `l2-map`, it was migrated under
that page type by `l2-map-1-to-2` in 0.7.0, and the migration chain still
registers it there. The lint's `_is_hub_page()` is what changes.

Consequences: 0 pages rewritten, the `l2-map` schema chain untouched.

### 3.2 One predicate, in `lib/`, imported by the lint

`lib/memory/page_types._is_folder_note_hub` and
`skills/wiki-health/lib/lint._is_hub_page` encode the same idea, written
independently, and they diverge (page_types excludes `index.md`; the lint
does not).

The issue records a layering reason not to share them. That reason does not
hold: the constraint is that `lib/` must not import from `skills/`, and the
dependency here runs the other way. `lint.py` already imports
`lib.memory.journal`, `lib.memory.quarantine` and `lib.memory.queue`.

**Decided:** `_is_folder_note_hub` in `lib/memory/page_types.py` is the single
predicate. The lint's folder-note branch is deleted and imports it. Per §3.1
the shared predicate keeps page_types' `index.md` exclusion, which means the
lint stops counting root `index.md` as a hub — the one behavioral change in
Part B, and the intended one.

That change must be **finding-neutral on the current wiki**: root `index.md`
carries no hub-rule finding today, and no non-hub rule may start firing on it.
§3.4's sweep is what proves this rather than assumes it. If the sweep does
differ, the difference is a finding to surface and decide on — never a
diff to absorb quietly into this train.

### 3.3 Global `lessons/lessons.md` — a narrow rule, not a wider predicate

`derive_type()` returns `lesson` for the root-level `lessons/lessons.md`
(rule 3), while disk says `hub`. The disagreement is unreachable in practice:
`_ensure_lessons_hub()` is the sole producer of that page and its pre-stamp
always wins under I1. The table still lies.

**Decided:** add a narrow rule 2b — root-level `lessons/lessons.md` derives
`hub` — and leave `_is_folder_note_hub` untouched.

Rejected: widening the predicate by dropping its `projects/` scoping. It is
the conceptually honest generalization, but the predicate is now shared
(§3.2), so the lint inherits any widening: more pages become hubs, and rules
like `hub-split-link-lists` begin firing on them. The scoping is also
deliberate — it exists so a project literally named `knowledge` cannot
false-positive. Buying table-honesty at the cost of an unmeasured lint blast
radius is the wrong trade in a defect train.

Accepted cost: "what is a hub" is now encoded in two places. Rule 2b carries a
comment pointing at this section.

### 3.4 Invariant

Part B rewrites **no pages** and produces **no new lint findings**. Both are
asserted, not assumed: a full lint sweep before and after must return the same
finding set.

## 4. Part C — deferred minors (#78), eight of ten

### 4.1 The recheckable gate is ordered wrongly

In `_retract_resolved_findings`, the `rule not in _RECHECKABLE_RULES: continue`
gate precedes the page-read that retracts findings on deleted pages. A
`held:<cls>` or `blocked:<cls>` finding against a page that no longer exists
therefore stays pending until the 30-day expiry.

**Fix:** hoist the page-existence check above the rule gate. A page being gone
is a *fact*, not a re-judgment — the reason the gate exists (never read the
absence of a fresh judgment as "resolved") does not apply to it. This strictly
increases correct retractions and cannot resolve a claim it did not check.

### 4.2 `prov is None` means two different things in wrap

`propose_and_apply` returns `prov is None` both for a genuinely held pending
write *and* for a noop-duplicate — content that normalized equal to disk,
yielding a synthetic, never-persisted entry whose qid is absent from the queue
directory. Wrap's update and create branches conflate them, so an unchanged
re-run reports an item as `held` citing a qid the friend cannot look up.

The discrimination already exists twice in the codebase: at wrap's own L1
branch (#49) and in the 0.8.1 lint fix. **Fix:** apply the same pattern at the
two remaining call sites. No new mechanism.

### 4.3 The remaining six

| Item | Fix |
|---|---|
| `decide()` docstring enumerates only accepted/declined/expired as immutable | Add `resolved`, which it already rejects |
| `_RESOLVED` (private) exported in `__all__` | Rename to `RESOLVED`; the issue's own condition — "if this file is touched for anything else" — is met |
| No test retracts an already accepted/declined/expired entry | Add the three cases; only resolved→resolved is covered today |
| `test_real_secrets_still_hit` lacks the exact #72 boundary | Parametrize the case: a guard word, a non-terminator character, then a terminator. **Assemble the fixture at runtime — never as a source literal.** See §7 |
| `test_merges_transport.py` imports mid-file | Move to top |
| Two `rglob` passes per `run_incremental_lint()` | Left as-is — see §4.4 |

### 4.4 Two minors stay, deliberately

`frontmatter-type-1/migrate.py`'s silent `continue` on an unreadable file
matches `trust-backfill-1`'s existing pattern, and wrap's raise-then-catch
matches the same file's other two call sites. Fixing only the named instance
would manufacture the inconsistency #78 was written to avoid; fixing the
siblings too would pull working, untouched files into a defect train for no
defect.

Each gets a one-line comment recording that consistency is the reason, so the
next reader does not re-derive this analysis. The double-`rglob` walk is a
performance observation on a tree of ~160 pages — noted, not acted on.

## 5. Part D — update's global tier

`/ren:update`'s closing steps call `rerender_all_project_claude_md()`, which
covers the **project** tier only. The **global** block in
`claude_user_dir()/CLAUDE.md` carries a doctrine index of absolute paths
pinned to the running version:

```
.../plugins/cache/ren-os/ren/<version>/doctrine/agent-orchestration.md
```

Nothing re-renders it on a version bump. After today's update those five paths
still read `0.8.0`. They resolve only because the 0.8.0 cache directory
happens to still exist; once it is GC'd they are dead links in a file injected
into every session.

**Fix:** `skills/update/SKILL.md`'s closing steps gain a global-tier step
beside the project one, calling the existing
`lib.adapter.claude_md.write_global_claude_md()`. Best-effort and
informational, exactly like its project-tier sibling — an update must not fail
on a CLAUDE.md render.

This is #64's shape one tier up: #64 wired the per-page re-render hooks and
closed the project-tier gap; the global tier was never in scope.

Today's stale block was already re-rendered by hand during the update
(`result: updated`, diff confined to the five version pins, everything outside
the markers preserved). Part D closes the recurrence, not the symptom.

## 6. Part E — doctor's cache-env check (#40)

`check_cache_env_hygiene` exists to catch `.venv` directories written inside
the immutable versioned plugin cache. It resolves the cache root from the
plugin invocation environment, and returns `skip` when that resolution fails —
which is precisely the case where a human is running `/ren:doctor` by hand to
find out what is wrong.

The result: the check has reported `skip` while the condition grew from one
stale `.venv` to four across three releases, and #40 still records "one".

**Fix:** resolve the cache root from the running framework's own module
location, which lies inside the versioned cache directory whenever the plugin
is installed — no environment variable required. Today's run proves the
current mechanism fails even in the best case: the check reported `skip` while
executing *from* `.../cache/ren-os/ren/0.8.1/`.

Three outcomes, distinguished — the current code collapses the last two into
`skip`:

| Situation | Result |
|---|---|
| Framework not running from a plugin cache (a repo checkout) | `skip` — correct, there is no cache to inspect |
| Cache root located, no stray `.venv` | `ok` |
| Cache root located but unreadable, or locatable only by a path that does not exist | `warn` — an unresolvable cache root is itself a finding |

The repo-checkout case must stay `skip`: `/ren:doctor` runs from this
repository during development, and a `warn` there would be noise on every
run.

**Remediation:** remove the four stale directories (0.7.6, 0.7.7, 0.7.9,
0.8.0) as part of the train, closing #40. They are regenerable uv
environments; `gc_stale_envs()` correctly leaves them alone because it prunes
`framework_root()/.envs/<v>`, a different location.

## 7. Part F — `_watermark_after` boundary tests

`skills/distill/lib`'s `_watermark_after` boundary behavior — the
same-timestamp case and the first-entry-blocked case — was logic-verified
during the 0.8.0 train but never test-pinned. Part F adds the tests. **No
production change**; if a test fails, that is a finding for a follow-up, not a
licence to edit the function inside this train.

## 8. Testing

TDD throughout. Every part below is a defect with observable behavior, so
every part gets a failing test before its fix.

- **Part A:** fence-free `../` fixture asserting neither reported nor
  rewritten; a genuinely escaping link still refused; the existing
  same-directory case unchanged.
- **Part B:** `derive_type()` table cases for root `index.md`, root
  `lessons/lessons.md`, and a project folder note; one predicate reachable
  from both call sites; full-sweep finding-set equality before and after.
- **Part C:** deleted-page retraction for a non-recheckable rule; unchanged
  re-run of wrap's update and create branches reporting neither a phantom
  `held` nor a qid absent from disk; the three decided-status retract cases;
  the #72 boundary case.
- **Part D:** rendered global block's doctrine paths track the running
  version; content outside the markers preserved byte-for-byte.
- **Part E:** `warn` (not `skip`) on an unresolvable cache root; `warn` naming
  each version on a seeded stale `.venv`; `ok` when clean.
- **Part F:** the two boundary cases named in §7.

### The push guard constrains one of these tests

`tests/lib/memory/test_scrub.py` carries an explicit comment stating that
fixtures below it must be assembled at runtime, because the pre-push guard
scans added lines with this very scanner. The 0.8.1 train was blocked twice
for putting secret-shaped literals below that line. The §4.3 boundary fixture
sits in that file and **must** be assembled at runtime.

Two further consequences, both learned the hard way in 0.8.1: the guard runs
the **installed** plugin's scrub, not the working tree's — so a verification
script written against a fixed local scrub can report CLEAN and be wrong — and
documentation of a scrub false positive cannot quote the offending string
literally. This spec describes the §4.3 shape rather than writing it.
